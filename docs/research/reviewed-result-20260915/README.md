# Canonicalを保持し、白紙Review XDWからReviewed Resultを作るための調査

調査日：2026-09-15。**設計調査であり、新機能の実装仕様・実装完了記録ではない。**

調査時は使い捨て文書で検証し、製品の実装・公開物を変更していない。後日の参照用にこの文書と検証JSONを開発リポジトリへ収録した。SDK本文、DLL、XDW原本、ローカルパスを含む元ログは収録していない。

## 1. 結論

この方式に必要な基礎操作は、現行Coreと公式SDKの組み合わせで実現できる見込みが高い。白紙の複数ページ作成、文字と任意の由来情報の保存、編集後の文字・位置・サイズの読取を実機で確認した。

既存の `read_review_edits()` は流用しない。現在は「原本に重ねた1ページの対象領域について、構造を維持して文字を訂正する」機能であり、追加・削除を拒否する。新機能は全ページ・全テキストの現在の状態を読む独立した入口にする。既存APIの規則を緩めて互換性を崩す必要はない。

実装前に押さえるべき点は次のとおり。

1. 文書・ページの識別を必須にし、元OCR領域の識別は任意の来歴にする。
2. 文字が0件でもページを残す。全削除後もページ属性で元文書と対応できる。
3. Viewerでコピーすると元OCR領域IDも複製される実例がある。重複を1対1の対応と誤認しない。
4. グループ・付箋の子の座標は親からの相対座標。ページ座標へ変換する。
5. 位置・サイズは保存後に再取得する。OCRの矩形や、生成時に指定したサイズで代用しない。
6. 将来の移動・サイズ変更の判定には、Canonicalだけでなく、生成直後のReview XDWの実測情報も残す。

## 4. 今回の実機検証結果

実OCRは実行せず、合成文書を生成してSDKで編集・保存・閉じる・再読込した。基準文書のハッシュを前後で照合した。新しいViewer操作は行っていない。

| 文字なしページ | 2ページを文字0件のまま保持 | 空ページを省略しない |
| 文書・ページ属性 | 保存・再読込、ページ挿入後も取得 | 文書/ページ対応の基礎になる |

## 5. 提案するデータ構造

以下は実装案であり、既存API・確定済みの新形式ではない。

### 5.1 Canonical

形式1.0/1.1と保存bundleを維持する。既存の `confidence` は既にnullを許容するため、「confidenceが入れられない」ことだけが分離理由ではない。固定的な領域ID・四角形・px/mm整合・空文字不可など、機械OCRの検証規則を自由編集へ持ち込まないことが主な理由である。

新規の標準OCRフローは全ページが揃ったCanonical 1.1を使うのが自然。旧bundleや一部ページだけのOCR結果は、ページ集合と元文書ページ数を明示検証する。未処理ページを「認識文字なし」とみなして白紙で補完しない。

### 5.2 Review Session（生成時の対応表）

| 項目 | 保存する意味 |
|---|---|
| review_id・形式版 | 校正作業セットの識別 |
| run_id・Canonical manifest hash・元XDW hash | OCR原記録への参照。絶対パスだけを識別に使わない |
| ページ対応表 | page_id、元ページ、Reviewページ、用紙寸法、生成時回転角 |
| 領域の生成時情報 | 元region_id、生成アノテーションID、初期文字、**保存後に実測した位置・サイズ・向き** |
| 生成環境 | Core/Integrations/API版、文字サイズやフォント等の生成設定 |
| 初期XDW hash | 編集開始前の状態の識別 |

元OCR矩形と、赤文字12ptで作ったテキスト枠は同じサイズとは限らない。移動やサイズ変更を調べるときは、生成直後の実測枠と校正後の実測枠を比較する。

XDW内には小さい識別情報を保存し、全文・比較用の情報は対応表に置く。対応表のハッシュをXDWに入れる場合、対応表に完成後XDWのハッシュも含めると循環参照になる。識別用の不変メタデータと、生成完了後のファイル一覧・ハッシュ記録は分ける。

### 5.3 Reviewed Result

正本は1文書のJSONまたは小さなbundleとし、JSONLはそこから作る派生出力を推奨する。JSONLだけでは文字0件のページが消えるため、ページ一覧を正本に持つ。

| 階層 | 主な項目案 |
|---|---|
| 文書 | schema/version、result_id、review_id、取り込み日時、取り込み元XDW hash、元文書参照、座標系、取り込み完了状態 |
| ページ | page_id、page番号、元ページ番号、width_mm、height_mm、rotation、items配列 |
| テキスト | item_id、text、ページ基準のx/y/width/height、回転角、縦書き/横書き |
| 任意の来歴 | 元OCR領域の参照、XDWに記録されていた由来、照合状態、診断 |

座標は左上原点、右方向+x、下方向+y、mm。内部計算はSDKの1/100mm整数を使い、保存時にmmへ変換すれば丸め誤差を抑えられる。

寸法の意味は**SDKが報告するテキストアノテーション枠の外接矩形**とする。印刷された文字のインク部分の範囲や、OCRの文字領域とは同一視しない。回転角を残しても、それだけで完全なViewer表示を再現できる形式にはならない。

item_idは取り込み結果内で一意に採番する。元region_id・SDKのhandle・列挙順をitem_idへ流用しない。取り込みをまたいだ永続的な項目同一性は、この初期設計では保証しない。

通常の検索・テンプレート処理はtext/page/geometryだけを読む。Canonicalや来歴の読み込みを必須にしない。取り込み時も、Session側に必要な情報が揃っていればCanonical全体との差分計算は不要。

### 5.4 来歴の状態

| 状態の意味 | 扱い |
|---|---|
| 記録された由来が対応表と一致 | 元領域への参照を保持。ただし全編集操作の追跡が証明されたという意味ではない |
| 属性なし | 由来不明。新規追加とは断定しない |
| 同じ由来が複数項目にある | コピー・分割等の候補として残す。1対1対応は未確定 |
| 属性破損・未知の由来・別reviewの属性 | 内容を結果から除かず、来歴に診断を付ける |
| 読取SDKエラー | 単なる属性なしと区別し、読取不能なら文書の確定を止める |

非テキストの親を無視してその子まで捨ててはいけない。付箋・グループを走査し、子のテキストを取得する必要がある。未知のコンテナーに対して正しい位置計算ができない場合は、黙って欠落させず未対応構造として報告する。

## 6. 取り込み・保存の流れ

1. 利用者が1文書のReview作業セットを選ぶ。フォルダー名だけで元文書を推測しない。
2. 保存済みXDWを同一ボリュームの専用一時領域へコピーし、コピー元とコピーのハッシュを照合する。
3. 読み取り専用で開き、文書ID・ページID・順序・寸法・ページ回転をSessionと照合する。
4. 全ページを再帰走査する。全テキストの現在の文字・実測枠・向きを取得し、親相対座標をページ座標へ直す。
5. 来歴を任意情報として照合する。重複・欠落等は診断に残し、文字の取り込みと分離する。
6. Reviewed JSON、必要なJSONL、取り込み元XDWの固定コピー、検証要約を新しい一時フォルダーに作る。
7. 再読込検証と入力の再確認後、フォルダー単位で新規の版として確定する。
8. 成功・失敗、ページ数、文字数、来歴が不明/重複の件数、保存先を日本語で表示する。

この方式は保存済みのスナップショットを確定する。Viewerで未保存の編集内容は対象外であり、ファイルハッシュ検査はViewerの編集セッション自体をロックするものではない。利用手順は「保存して閉じる→取り込み」とする。

最初のReview XDW、編集用の作業XDW、取り込み済みXDWは役割を分ける。利用者は作業XDWを上書き保存できる。取り込みは新しいresult_idで版を追加し、以前のReviewed Resultを上書きしない案を推奨する。容量増加は伴うが、将来の比較を再現できる。

同じXDW hashを再取り込みした場合は「同一の保存内容を取込済み」と案内できる。新しい結果を作るか既存結果を返すかは実装仕様として確定する。保存・取り込み成功は全文の人手確認を機械が証明するものではない。

## 7. 初期版の推奨境界と必要な実装

### 推奨する利用仕様

- OCR開始と取り込みは別BAT。取り込み単位は1文書。
- 元と同じページ構成・寸法の白紙XDWを1文書1ファイルで作る。認識0件のページも作る。
- 生成文字は赤を初期値とする。取り込み対象は色で限定しない。
- 文字の修正・追加・削除・移動・コピーを扱う。
- ページの追加・削除・並べ替え・回転・用紙寸法変更は初期版では未対応として検出する。
- グループ/付箋内の文字も対象にするなら、親相対座標の変換を必須にする。多段構造等の未検証組み合わせは検証後に対応範囲へ加える。
- 空文字や空白だけの項目は原状態として保持し、診断を付ける案を推奨。検索用の除外は別段階にする。
- 列挙順は読み順とみなさない。初期版は取得順を記録し、必要なら別フィールドに座標順を作る。段組・表・縦書きの意味的な読み順推定は範囲外。
- 文書/ページの識別不整合は取り込みエラー。任意の領域来歴の曖昧さは警告・診断。

### 実装する単位

1. **新Review生成**：Canonicalの全ページ確認、白紙作成、赤文字配置、Session・識別属性・生成直後実測情報の保存。
2. **新Reviewed読取**：全テキスト走査、親座標変換、実測枠と文字属性、任意来歴の取得。
3. **Reviewed保存/読込/JSONL**：新しい形式版・検証・不変の版保存・文書単位確定。
4. **起動と状態管理**：OCRジョブにReview工程を追加、別の取り込みBAT、成功/失敗/未処理を表示。
5. **日本語文書と配布確認**：使い方、範囲外操作、再取り込み、Portableへの収録。

現行Coreには必要なRaw APIが既にある。初期実装はIntegrations側の小さなSDK境界で構成できる見込みで、Coreの公開APIを拡張することを前提にしない。公開配布物の更新・公開は別工程。

生成の現行補助 `add_text()` は1領域ごとに文書を開いて保存する。全ページ・大量文字へそのままループ流用すると保存回数が増える。新生成では1つの作業文書を開いてまとめて追加し、最後に保存・閉じる・再読込する設計にする。性能値は未測定。

## 8. 実装時の受入確認

| 分類 | 必須ケース |
|---|---|
| 生成 | 1ページ、複数ページ、混在寸法、文字0件ページ、全ページ文字0件、同文同位置/同文別位置の領域 |
| 文字 | 日本語、Unicode補助文字、改行、空白、長文、新規追加、削除、全削除、空文字 |
| 位置 | 移動、サイズ変更、回転、縦書き、付箋/グループ、多段構造、ページ端やはみ出し |
| 来歴 | 編集維持、コピーによる重複、属性なし、属性破損、別reviewからのコピー |
| ページ識別 | 別文書、同寸法ページ入替え、コピー、削除、180度回転、文書/ページ属性欠落 |
| 保存 | 途中中断、出力衝突、同一内容の再取込、入力の同時変更、原本・Canonical・過去版の不変 |
| 起動/配布 | 日本語・空白パス、取消し、未保存/使用中の文書、Portable同梱Python、選択文書1件 |

### 残る未検証事項

- 新しい白紙の複数ページ文書をViewerで編集・保存・再表示したときの表示、編集性、新文書/ページ属性の保持。
- グループの多段化、付箋上のグループ等の組み合わせと、回転した子のページ座標の実表示照合。
- 大量領域の所要時間・メモリ・XDW容量、文字の重なりやすさ。12pt固定は読みやすさや枠内収容を保証しない。
- DocuWorks 9.1本体やPortable同梱環境での新フローの実行。今回のPython 3.13＋製品DLLの結果から一般化しない。
- ファイル使用中、途中中断、JSON/JSONL同時確定等の完成した取り込み処理としての試験。

これらは実装時の受入条件として残す。調査段階では主要な技術選択に必要な情報は揃っており、製品実装や公開完了を意味しない。

## 9. 将来の差分分析を追加するとき

1. Sessionの生成直後情報、Canonical、対象版のReviewed Resultと取り込み元XDWを読む。
2. 由来が一意に照合できる領域を比較する。文字は元文字と、移動/サイズは生成直後の実測枠と比較する。
3. 重複や由来なしは、文字・位置・周辺配置から候補を作り、推定と記録された対応を分ける。
4. 分割・結合は多対多の独立した対応表へ保存する。元データを書き換えない。
5. 曖昧な候補だけ人が確定する。

初期状態と最終状態だけでは、途中の編集順序や編集者は復元できない。元領域が消えたように見えても、IDを失った作り直しと削除は区別できない場合がある。細かい編集履歴が必要になった場合は別の記録方式が必要となる。
